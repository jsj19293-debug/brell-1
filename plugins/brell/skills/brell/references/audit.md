# 오류검토 및 검수 (`/검수`)

제작자가 `/검수` 또는 "검수해줘"라고 하면 언제든지 이 순서로 한다. **메인 프롬프트와 로어북을 둘 다** 읽고 본다. 결과는 수정권고 보고서로 내고, 승인받은 항목만 반영한다. 편집창 조작은 `sites/` 안의 해당 사이트 파일을 따른다.

## 1. 전문 읽기

- 대상: 메인 프롬프트, 로어북 전 항목(이름·켜는 키·끄는 키·내용), 시작상황, 작품소개.
- 제작자가 원고를 대화창에 붙여 주면 그것을 읽는다. 편집창에서 읽을 때는 해당 사이트 파일의 읽기 요령을 따른다.
- 다 읽기 전에는 판정하지 않는다. 못 읽은 부분이 있으면 보고 첫머리에 적는다.

## 2. 검토 항목

항목마다 **문제 / 문제없음 / 확인 필요** 중 하나로 판정한다. 문제는 위치(항목 이름)와 근거 문장을 같이 적는다.

### 공통
- 사이트 규격표의 글자수·키워드 개수를 넘었는가. 글자 수는 실제로 재서 적는다.

### 세계관
1. 세계관에 모순점이 있는가. 서로 어긋나는 사실, 연도 계산, 메인과 로어북의 설명 차이.
2. 모순되는 단어가 있는가. 같은 대상을 다르게 부르는 말, 뜻이 반대로 읽히는 표현.
3. 세계관에 치명적인 결함이 있는가. 작품의 전제가 무너지거나 진행이 막히는 설정.
4. 이용자가 즐길 콘텐츠가 부족한가. 할 수 있는 행동, 갈 곳, 사건, 목표가 빈약한 곳.

### 캐릭터
1. 캐릭터가 너무 단조로운가. 성격과 핵심욕망이 같은 방향이라 갈등이 안 생기는 경우(`lorebook.md` 3-3 평면·입체).
2. 캐릭터 성향이 중복되는가. 성격태그, 기본 온도 조합, 핵심욕망이 겹치는 인물.
3. 말투가 중복되는가. 말투특징·말투예시·어미·호칭이 겹치는 인물.
4. 똑같은 캐릭터를 복사해 붙여 넣었는가. 문장 틀이나 문장이 그대로 반복되는 항목.
5. 캐릭터 성격에 모순이 있는가. 태그와 행동 문장, 말투가 서로 어긋나는 곳.
6. 캐릭터 DB와 로어북이 일치하지 않는가. 이름·코드·나이·외형·성격태그·관계를 메인 DB ↔ 캐릭터 로어북 ↔ 관계도에서 전수 대조.

### 시스템
1. SVG 링크가 잘못됐는가. 제작자의 Cloudflare Workers 주소·경로와 대조한다. Workers 목록을 받지 못했으면 "확인 필요"로 두고 목록을 요청한다.
2. SVG 이미지가 안 나오는가. 링크를 새 탭에서 열어 실제로 그려지는지 본다.
3. 시스템상 모순이 있는가. 규칙끼리 부딪히는 곳, 모드 설명과 실제 로어북의 차이.
4. 오류 발생 확률이 높은가. 모델 판단이 필요한 발동 조건, 개수가 안 맞는 선택지, 한 줄에 여러 규칙.
5. AI가 시스템을 잘 이해하는가. 성능이 낮은 AI가 압축어·약어·기호·전문 용어를 알아들을지 조사하고, 어려우면 풀어 쓴 안을 낸다.
6. 이모지 치환 규칙이 잘 되는가. 치환 전후 표기, 변형 문자(FE0F) 유무, 공백 차이로 키가 어긋나지 않는지.
7. 로어북 발동 키가 맞는가. 이름만 단독으로 쓴 키, 부분일치 함정(`!X`↔`!!X`), 같은 키를 여러 항목이 쓰는 경우, 챗플 완전일치(`lorebook.md` 4절).
8. 시스템에 치명적인 결함이 있는가. 모드가 안 켜지거나 안 꺼지는 경우, 진행이 멈추는 경우.

### 이미지 출력형식
1. 메인의 이미지 출력형식대로 출력했을 때 이미지가 안 나오는가.
2. 이미지 검열이 덜 됐는가. 사이트 기준에 맞게 가려야 할 부분이 가려졌는지.
3. 이미지 링크가 이상한가. 주소 형식, 오타, 열리지 않는 링크.
4. 이미지 코드가 안 맞는가. 캐릭터 고유코드·상황코드와 실제 파일 번호 대조.

### INFO
1. 출력 토큰을 많이 먹는가. INFO 양식 한 번 출력의 글자 수를 재서 적는다.
2. 인포창이 너무 비대해지지 않았는가. 매 턴 꼭 필요하지 않은 줄.
3. 정보량이 생각보다 없는가. 상태 유지에 필요한데 빠진 줄(모드·장소·시간·호감도 등).
4. 이용자 친화적인가. 이용자가 한눈에 읽기 쉬운지, 의미를 알 수 없는 기호가 있는지.
5. INFO 고정 문자열이 메인 양식 ↔ 시작상황 ↔ 로어북 키와 글자 단위로 같은가.

## 3. 수정권고 보고서

대화창에 낸다(제작자가 문서를 원하면 그때 문서로).

- 머리말: 무엇을 읽었는지, 못 읽은 것, 발행하지 않았다는 사실.
- 분류별(공통·세계관·캐릭터·시스템·이미지·INFO)로 표를 하나씩 만든다: `번호 | 항목 | 판정 | 위치 | 근거 | 수정안`.
- 문제는 심각도를 붙인다: **치명**(작동 안 함) / **오작동**(가끔 틀림) / **개선**(작동은 함).
- 문제없음으로 확인된 항목도 한 줄씩 남긴다.
- 승인안: 1안(치명만) / 2안(+오작동) / 3안(+개선). 방향 선택이 필요한 항목은 따로 묻는다.
- 위치는 내부 번호가 아니라 항목 이름으로 적는다.

## 4. 승인분 반영

1. 원본을 `window` 변수에 깊은 복사로 보관한다.
2. 수정은 정확한 문자열 치환으로 하고, 치환마다 예상 횟수와 실제 횟수를 대조한다. 하나라도 어긋나면 아무것도 반영하지 않는다.
3. 일괄 변환(코드→이름, 한자→한글)은 제외 대상을 먼저 정한다: DB의 코드 열, URL 안의 코드, `이름(코드)` 표기, 코드 자체가 의미인 시스템 지시, 제작자가 직접 써 준 문안. 바꾼 뒤 조사(은/는·이/가·을/를·과/와)를 받침에 맞춘다.
4. 바뀐 줄만 뽑아 전부 읽고 어색한 결과(`하유하(하유하)`)를 고친다.
5. 압축어를 풀 때 압축 정도는 유지한다(문장으로 늘이지 않는다).
6. 반영 후 편집창 상태가 의도와 같은지 비교한다. 에덴은 서버 쓰기 요청이 없었는지 확인한다.
7. 에덴 원본을 고쳤으면 다른 사이트 이식본에도 같은 수정 목록을 올린다.
8. 보고: 반영한 것, 안 한 것(이유), 해석해서 정한 것.
